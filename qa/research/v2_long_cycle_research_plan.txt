# V2 Research Test — Deferred Diagnostic Plan

Date: 2026-09-19
Status: Deferred / not yet implemented

## Problem

During an endurance run, one V2 collection cycle became abnormally long (about 12 hours) after a Bybit retry event, then still saved a snapshot. The following cycle returned to normal duration.

Short manual network-loss experiments did not reproduce the issue.

## Research goal

Determine where the long delay happens inside one V2 collection cycle.

The objective is not to change behavior yet, but to add enough observability to identify the exact stage that stalls when the problem happens again.

## Diagnostic logging to add later

Add timestamps around the main stages of one V2 cycle.

Suggested events:

REQUEST_START page=<n>
REQUEST_END page=<n>

NORMALIZE_START
NORMALIZE_END

REFERENCE_START
REFERENCE_END

DB_SAVE_START
DB_SAVE_END

Optionally also log:

CYCLE_START
CYCLE_END
RETRY_START page=<n> attempt=<n>
RETRY_END page=<n> attempt=<n>

Each event should include an absolute timestamp.

## What this should tell us

If the next abnormal cycle looks like:

14:00 REQUEST_START page=4
02:00 REQUEST_END page=4

then the delay is inside the Bybit HTTP request/retry path.

If it looks like:

REQUEST_END
14:00 DB_SAVE_START
02:00 DB_SAVE_END

then the delay is inside the PostgreSQL save path.

If the delay appears between another START/END pair, that stage becomes the next research target.

## Research method

1. Add diagnostic timestamps without changing normal V2 behavior.
2. Run V2 for a long endurance session.
3. If an abnormal cycle appears again, compare the timestamps.
4. Identify the stage containing the large time gap.
5. Create a targeted reproduction test for that specific stage.
6. Only after the cause/condition is better understood, implement a fix.
7. Retest the defect and run regression checks.

## Current research results

### Experiment 1 — network loss until retries are exhausted

Observed:
- collection started normally;
- Bybit request failed;
- retries were exhausted;
- the current cycle did not remain hanging for hours;
- the next scheduled cycle started normally.

Result:
NOT REPRODUCED

Conclusion:
A simple temporary network outage with retry exhaustion is not sufficient by itself to reproduce the original long-cycle defect.

### Experiment 2 — network restored before request timeout

Observed:
- internet was interrupted during collection;
- connection was restored before the request timeout;
- no error/retry was logged;
- collection continued normally.

Result:
NOT REPRODUCED

Conclusion:
A short interruption that resolves before the request timeout also does not reproduce the original defect.

## Current conclusion

The original 12-hour V2 cycle is not yet reliably reproducible.

Further random network interruption tests are unlikely to be useful without better instrumentation.

Next step:
add stage-level timestamp logging and repeat an endurance run.
